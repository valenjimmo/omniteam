## Findings

### [HIGH] Family approval can demote an existing team owner, admin, or coach

- Evidence: `supabase/migrations/202611190003_family_registration_baseline.sql:182-184`
  upserts the applicant's membership with `do update set role='PARENT'`. The
  canonical access model explicitly allows a parent to remain an admin while
  retaining the guardian link (`docs/reference/ACCESS_MODEL.md:13-18`), and the
  original membership creation preserved an existing role
  (`supabase/migrations/202609140004_team_access_and_parent_registration.sql:380-383`).
  The DEV-04 database suite tests a new parent but has no pre-existing staff
  membership case (`supabase/tests/family_registration_baseline.sql:35-57`).
- Impact: approving a family registration for an existing OWNER, ADMIN, or COACH
  silently replaces their staff authority with PARENT access. For an OWNER this
  can remove the user's ability to administer the team.
- Minimal fix: in a forward migration, reactivate an existing membership without
  changing its role; assign `PARENT` only on insert. Keep the independent
  `family_guardians` relationship as the source of family access.
- Acceptance tests: approve registrations for existing OWNER, ADMIN, COACH,
  inactive staff, and new users; preserve each existing role, reactivate inactive
  membership, create the guardian link, and prove the behavior is team-scoped.

### [MEDIUM] Direct registration calls bypass part of the configured intake contract

- Evidence: the client requires a configured program and required custom answers
  in `src/modules/omniathlete/registration/model.ts:165-172`, but
  `submit_family_registration` never validates `requestedProgramId`,
  `familyAnswers`, or swimmer `answers`
  (`supabase/migrations/202611190003_family_registration_baseline.sql:101-132`).
  It accepts any date-shaped birth date at lines 103-108, while approval casts
  that value to `date` at lines 167-171. The client only checks that birth date
  is present (`src/modules/omniathlete/registration/model.ts:157-161`). Current
  direct-RPC tests cover email, legal sex, and roster group, not these cases
  (`supabase/tests/family_registration_baseline.sql:28-31`).
- Impact: callers can omit team-configured required answers or submit an
  unauthorized/nonexistent program preference. An impossible date can enter the
  pending queue and then make approval fail transactionally instead of being
  rejected at submission.
- Minimal fix: centralize the supported configuration validation at the trusted
  submission RPC, require selected program IDs to exist in the captured active
  configuration, validate required family/swimmer answers by type, and reject
  birth dates that cannot be safely cast to a calendar date. Mirror calendar-date
  validation in the client.
- Acceptance tests: direct RPC rejection for impossible dates, missing required
  family/swimmer answers, invalid single/multi-select values, and absent/foreign
  program IDs; valid configured payloads still submit and approve.

### [MEDIUM] The committed Supabase `Database` type is a partial handwritten projection

- Evidence: `src/lib/supabase/database.types.ts:1-2` says the file was generated
  but also says generation must wait for local Supabase. It lists only seven
  tables and six RPCs (`src/lib/supabase/database.types.ts:5-67`) although the
  tracked schema contains many additional public tables and functions, including
  all family-registration tables/RPCs. DEV-01 required generated row, insert,
  update, enum, relationship, and RPC types for the final schema, while the only
  consumer currently imports the narrow `teams` type
  (`src/app/dashboard/setup/[teamId]/setup-editor.tsx:8-10`).
- Impact: the artifact can drift silently from migrations and cannot provide the
  promised compile-time contract for most Supabase queries or RPCs. Passing
  typecheck verifies only the handwritten subset.
- Minimal fix: generate the complete type file from a database with every tracked
  migration applied, commit it without manual pruning, and add a reproducible
  generation/check command. Replace only touched incompatible local casts.
- Acceptance tests: generation succeeds from a clean fully migrated schema;
  representative club, checkout, setup, family-registration, and tenant tables
  and RPCs are present; regeneration produces no diff; typecheck passes.

### [LOW] Subscription workflow reference still documents the pre-DEV-02 journey

- Evidence: `docs/reference/SUBSCRIPTION_WORKFLOW.md:3` says `/subscribe` collects
  only team name/timezone and then opens `/dashboard`; current onboarding also
  collects identity/location/contact data and redirects to the authorized setup
  checklist (`src/app/subscribe/page.tsx:33-44`). The reference attributes the
  model only to the 2026-09 migration at line 9 and omits the 2026-11 profile and
  onboarding migrations.
- Impact: operators and future implementers receive an obsolete description of
  the active onboarding contract and completion destination.
- Minimal fix: update the reference to the six stages, public-plan mapping,
  canonical team profile, atomic completion, and setup redirect; list the
  migrations that extend the original model.
- Acceptance tests: the reference matches the current UI/RPC fields, plan-key
  boundary, persistence owner, and post-completion route, without redefining the
  canonical product hierarchy.
