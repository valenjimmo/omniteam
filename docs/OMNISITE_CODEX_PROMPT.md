# Codex build prompt: OmniSite

Build OmniSite in this repository according to `docs/OMNISITE_DESIGN.md`. Read `AGENTS.md`, `docs/OMNITEAM_STRUCTURE.md`, `docs/PRODUCT_STRUCTURE.md`, `docs/TENANT_ISOLATION.md`, `docs/ACCESS_MODEL.md`, and `docs/DATABASE_CHANGE_WORKFLOW.md` first. Preserve OmniTeam's eight-module hierarchy and do not rename OmniSite features.

Implement the first delivery slice end to end, including database migrations, RLS, storage policies, server authorization, template manager, team editor, public renderer, and meaningful tests. OmniSite must work for a team that purchased only OmniSite. Optional OmniAthlete integration may display only approved group information when both entitlements are active. Do not expose swimmer, family, attendance, or payment data on public pages.

Requirements:

1. Ship 2–3 responsive, accessible predefined layouts. Keep the renderer in code with a strict, versioned section schema. Add a platform-owner-only template manager where I can create, duplicate, preview, publish, and retire template records by configuring supported layouts, sections, defaults, and starter pages. Do not require a code deployment for a new template variant; a brand-new renderer/section type may require one.
2. Let a team OWNER or authorized OmniSite manager choose a template, upload/replace its logo, choose and preview team colors, edit starter pages and navigation, save drafts, and publish. Validate images and color contrast. Use safe rich text and links; never accept executable HTML, CSS, or JavaScript from editors.
3. Keep shared templates separate from tenant sites. Copy or version template content on selection. Template edits must not silently rewrite a team's drafts or published site. Render public visitors from an atomic published snapshot only; include rollback and clear unavailable behavior.
4. Enforce active team, OmniSite entitlement, and module permission on every mutation. Scope all team-owned SQL, storage paths, cache entries, and public lookups by `team_id`. Use RLS plus composite tenant foreign keys, immutable tenant IDs, and exact team resolution. The platform owner's template-catalog write privilege must be separate from read-only support sessions.
5. Provide `/sites/{team-slug}` as the initial public route. Structure hostname resolution so verified custom domains can be added later. Implement Home/About/Contact pages first. Add News and Events as OmniSite-owned content in the next increment only if the first slice is complete and validated. Other module feeds must be explicit, approved adapters gated by both entitlements.
6. Update test purge, team hard-delete, and team archive behavior for OmniSite rows and stored assets. Do not accidentally delete shared templates or global Auth users. Follow the migration workflow; never run destructive scripts or migrations against a remote project without identifying the target and reconciling history.
7. Add tests that prove: team A cannot read/edit/publish team B drafts or assets; a cross-team page/asset relationship is rejected; users lacking OmniSite entitlement or MANAGE access cannot edit/publish; visitors cannot read drafts; archived/unpublished teams are unavailable; a template update does not alter an existing published site; team colors and logos appear in responsive previews and publication.

Use existing Next.js, Supabase, and repository conventions. Keep the code organized under an OmniSite module boundary with small interfaces for optional cross-module content. Update relevant docs and give a concise report of completed behavior, migration steps, test results, and remaining limitations. Do not claim a remote database or Vercel deployment was updated unless you verified it.
